판단 1  —  LLM 호출 비용 통제 : 호출 전 차단 게이트 설계

상황
배포 전 테스트에서 일일 API 호출 한도가 예상보다 빠르게 소진됐습니다. 배포 일정은 얼마 남지 않은 상태였습니다.
원인
요청 처리 흐름을 단계별로 좁혀 검증한 결과, 같은 질문의 재조회와 애초에 답변이 불가능한 요청(과정에 등록된 자료가 없는 경우)이 호출량의 상당 부분을 차지하고 있었습니다.
대안
① 한도 상향   ② 더 저렴한 모델로 교체   ③ 호출 전 차단 게이트
선택
③. ①은 비용을, ②는 답변 품질을 대가로 지불하는 임시 조치이며 소진 속도 자체는 개선되지 않습니다. 소진의 주 원인이 불필요한 호출이므로, 해당 호출을 제거하는 것이 근본 해결이라고 판단했습니다.
실행
수강 권한 → 입력 길이 1,000자 → 자료 유무 → 일일 한도(전체 500 / 1인 50) 순서로 모델 호출 전에 검사하도록 게이트를 앞단에 배치하고, 동일 분석 요청은 저장된 결과로 응답하도록 캐시를 뒀습니다.
결과
배포 일정 내 해결, 이후 한도 소진 없이 운영 중입니다.

판단 2  —  RAG 인용 검증 : 범위 밖 인용 폐기 및 출처 분리 표기

상황
RAG 답변에 인용 번호가 붙어 나왔지만, 실제로 전달한 자료의 범위를 벗어난 번호가 섞여 나오는 경우가 있었습니다. 훈련생이 링크를 눌렀을 때 근거가 없는 자료로 연결될 수 있는 상태였습니다.
대안
① 인용을 그대로 노출   ② 인용 기능 자체를 제거   ③ 검증 후 걸러서 노출
선택
③. 학습 서비스에서 근거 링크는 답변만큼 중요하다고 봤습니다. 다만 다만 잘못된 근거로 연결되는 링크는 답변 전체의 신뢰도를 떨어뜨리므로, 검증을 통과한 인용만 노출하기로 했습니다.
실행
답변이 실제로 인용한 자료만 링크로 노출하고 범위 밖 인용 번호는 폐기했습니다. 자료에 없는 내용은 지우는 대신 "일반 지식"으로 분리 표기해, 답변은 살리되 출처가 있는 것과 없는 것을 구분했습니다. RAG로 해결되지 않은 질문은 담당 강사 Q&A로 자동 이관해 훈련생이 같은 질문을 반복하지 않도록 했습니다.

판단 3  —  대시보드 지표 산출 기준 통일 : 산출 불가 구간 미표시 처리

상황
대시보드의 진도율·기간 경과율·이수 요건 충족은 관리자와 강사가 각각 다른 기준으로 보고 있었고, 데이터가 없는 구간에서 무엇을 보여줄지 정해져 있지 않았습니다.
대안
① 0으로 채움   ② 직전 값 유지   ③ 미표시
선택
③. 이 지표는 훈련생의 이수 판정과 연결됩니다. 0%와 "아직 산출 불가"는 의미가 다르지만 화면에서는 구분되지 않아, 잘못된 수치가 이수 판정에 반영될 위험이 있다고 판단했습니다.
실행
세 지표를 서버 집계로 옮겨 관리자·강사 산출 기준을 통일하고, 산출 불가 구간은 미표시로 처리했습니다. 훈련생에게는 개별 수치 대신 익명 진도 순위로 제공했습니다.
확장
같은 원칙을 기동 조건에도 적용했습니다. API 키가 없으면 AI 기능만 비활성화하고 앱은 정상 기동하도록 해, AI가 LMS 본체를 멈추지 않게 했습니다.

판단 4  —  기능 구현 검증 체계 설계 : 4단계 판정 기준 수립

상황
취업캠퍼스 · 몰입클라쓰 · 비즈워크래프트 · LXP 4개 서비스가 각자 기능 명세를 갖고 있었지만, 명세에 적힌 것이 실제로 구현돼 있는지 확인된 적이 없었습니다. 팀이 소규모라 "된다고 알고 있는 기능"과 "실제로 되는 기능"의 차이를 아무도 추적하지 못하는 상태였습니다.
대안
① 구현 / 미구현 2단계   ② 구현 / 부분구현 / 미구현 / 확인필요 4단계
선택
②. 2단계로 판정하면 근거가 불충분한 항목을 임의로 어느 한쪽에 배정해야 하고, 그 경우 감사 결과 전체의 신뢰도가 떨어집니다. 확인이 불가능하다는 사실 역시 감사 결과이므로 별도 상태로 분리했습니다.
실행
기능 요구사항 211건을 엔티티 · 서비스 · 템플릿 코드까지 따라가며 4단계로 판정하고, 상태별 색상(초록 / 노랑 / 빨강 / 파랑)으로 구분한 감사 리포트로 정리했습니다.

판단 5  —  판정 근거 재검증 : 오탐 정정 및 반복 오기재 일괄 수정

상황
1차 판정을 마친 뒤, 판정 근거로 적어둔 문구 중 일부가 실제 코드와 어긋난다는 것을 발견했습니다. 같은 문구가 여러 항목에 반복 인용돼 있었습니다.
선택
감사 결과의 신뢰도는 판정 건수가 아니라 판정 근거의 정확도에 좌우된다고 판단해, 1차 판정을 확정으로 두지 않고 근거를 재검증했습니다.
실행
근거가 부정확했던 3건을 코드 재확인으로 정정하고, 반복 오기재된 근거 문구는 전수 검색해 일괄 정정했습니다.
결과
구현 완료 판정이 21건 → 23건으로 보정됐습니다. 211개 항목 전체에 코드 라인 단위 근거가 남아, 이후 개발 우선순위를 추측이 아니라 근거로 정할 수 있게 됐습니다.

판단 1  —  전 구간 로컬 추론 채택 : 진료 정보 외부 전송 차단

상황
요약과 쉬운말 변환에는 정확도와 응답 속도가 앞서는 클라우드 LLM API를 쓰려고 했습니다. 개발 중간에, 이 서비스가 실제로 다루는 대화가 진료 내용과 복약 지시라는 점을 다시 봤습니다.
대안
① 클라우드 전면 사용   ② 민감 구간만 로컬   ③ 전 구간 로컬
선택
③. ②는 어디까지가 민감 구간인지 매번 판정해야 하는데, 실제 대화에서는 진료 내용과 일상 대화가 섞여 나타납니다. 판정이 한 번만 틀려도 진료 내용이 외부로 전송되므로, 구간을 나누지 않고 전 구간을 로컬로 처리하기로 했습니다.
비용
응답 속도와 요약 품질을 일부 양보했습니다. 다만 요약은 통화가 끝난 뒤에 처리하는 단계라 실시간성이 덜 중요했고, 실시간이 필요한 자막(STT)은 경량 모델로 별도 처리하면 된다고 봤습니다. 양보한 항목이 서비스의 핵심 사용 경험에 해당하지 않는다고 판단했습니다.
실행
요약·쉬운말 변환은 로컬 Ollama, STT는 Faster Whisper, 화자 분리는 Resemblyzer로 전부 로컬 구동했습니다. 학습 환경과 추론 환경이 달라 생긴 문제들은 원인을 찾아 해결하고 기간 내 동작하는 결과물을 완성했습니다.

판단 1  —  벡터 + 그래프 하이브리드 검색 설계 : 관계 조건 처리

상황
FAISS 의미 검색은 "저렴한 흑돼지집"은 찾았지만 "성산일출봉 근처 현지인이 가는 흑돼지집"은 못 찾았습니다. 질문이 장소와 업종과 인접성의 관계를 담고 있는데, 벡터 유사도는 관계를 따라갈 수 없기 때문이었습니다.
대안
① 프롬프트 개선   ② 메타데이터 필터 추가   ③ 그래프 DB 병행
선택
③. ①②는 조건이 늘어날 때마다 규칙을 덧붙여야 하고, 항목 간 관계 자체를 표현하지 못합니다. 데이터가 이미 관계 구조를 갖고 있으므로 검색도 관계 기반으로 수행하는 것이 적합하다고 판단했습니다.
실행
Restaurant ↔ Location ↔ Cuisine ↔ Tourist_Spot 다중 hop 스키마를 Neo4j로 설계하고, FAISS로 후보군을 좁힌 뒤 Neo4j 경로 탐색으로 재정렬하는 하이브리드 구조를 만들었습니다. LLM에는 검색 결과와 함께 추천 근거 경로를 전달했습니다.

판단 2  —  할루시네이션 차단 : 프롬프트 지시 대신 컨텍스트 제한

상황
초기 답변이 데이터에 없는 가게를 언급하거나, "근처" "가까운"처럼 검증할 수 없는 표현으로 위치를 설명했습니다.
선택
프롬프트 지시는 준수 여부를 확인할 방법이 없습니다. 구조적으로 불가능하게 만들어야 검증이 가능하다고 판단했습니다.
실행
LLM 컨텍스트에 FAISS 검색 결과만 전달해, 데이터에 없는 가게는 답변 자체가 불가능하게 했습니다. 위치는 가맹점·관광지에 위도/경도를 추가해 컨텍스트에 함께 넘기고, 모호한 표현 대신 차량 이동시간으로 답하게 했습니다.

판단 1  —  가입 요건 필터와 추천 모델 분리 : 책임 범위 구분

상황
금융 상품에는 최소투자금액·권장투자기간·투자성향처럼 충족하지 못하면 애초에 가입이 불가능한 조건이 있습니다. 이 조건까지 학습 데이터에 넣어 모델이 알아서 걸러내게 할 수도 있었습니다.
선택
모델은 확률로 답하기 때문에 가입 불가 상품을 낮은 확률로 추천합니다. 반드시 지켜야 하는 규칙과 추천의 품질은 성격이 다르므로, 규칙은 룰로 확정하고 모델은 품질만 맡도록 책임을 분리했습니다.
실행
TabNet 위험군 분류 → 룰 기반 가입조건 필터 → FAISS L2 유사도 추천의 3단계로 나누고, 가입 불가 상품은 추천 단계에 도달하기 전에 룰로 제거하고, 예상 수익률 기준 상위 10개로 좁힌 뒤 유사도 탐색을 돌렸습니다.

판단 2  —  설명 가능성 기준 모델 선정 : TabNet 채택

상황
고령층 대상 금융 상품 추천 서비스로, 판정 사유를 설명할 수 없으면 사용자가 추천 결과를 신뢰하기 어렵습니다.
대안
① XGBoost   ② RandomForest   ③ TabNet
선택
③. TabNet은 attention mask로 개인별로 어떤 항목이 그 판정을 만들었는지 추적할 수 있습니다. 표형 데이터 정확도와 설명력을 함께 비교한 뒤 선택했습니다.
결과
위험군 분류 정확도 65%, 키워드 매칭 baseline 대비 추천 정확도 +27%p · 취약 고객 탐지 민감도 +23%p. 실 개인 금융 데이터가 없어 KOSIS·보건복지부 분포 기반 합성 데이터로 평가했으며, 실서비스 도입 효과가 아닙니다.
